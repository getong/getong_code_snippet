* 概念与职责

MCP、RAG 和 Qdrant 分别解决不同的问题：MCP 规范 AI 应用如何访问外部工具与数据，
RAG 组织检索与生成的流程，Qdrant 则提供向量存储和检索能力。

它们可以组合使用，但彼此并不绑定：RAG 不一定通过 MCP 实现，也不一定使用 Qdrant；
MCP 服务端同样可以连接文件系统、关系数据库或其他业务 API。

** MCP：工具与数据的接入协议

MCP（Model Context Protocol，模型上下文协议）定义了客户端与服务端之间的通信方式。
服务端可以公开工具、资源和提示词模板，供支持这些能力的 AI 应用使用。

严格来说，Codex 这类 AI 应用属于宿主（Host），由其内部的 MCP 客户端与服务端通信。
下文为便于说明，将这类应用统称为“AI 客户端”。

MCP 不限制服务端的实现语言。Rust、Python、TypeScript、Go 等语言都可以用于实现服务端，
关键是遵循协议，并与客户端支持的版本和能力相匹配。

参考：[[https://modelcontextprotocol.io/docs/learn/architecture][MCP 官方架构说明]]。

** RAG：先检索，再结合资料生成回答

RAG（Retrieval-Augmented Generation，检索增强生成）是一种应用架构：先从外部知识源
检索相关资料，再把资料作为上下文交给大模型，辅助生成回答。

RAG 通常包含资料处理、索引构建、查询检索、上下文组织和回答生成等环节。
它不是一个固定的服务，也不是向量数据库的别名。

** Qdrant：向量与相关数据的存储、检索层

Qdrant 可以存储向量及其关联的 Payload，并执行相似度检索和条件过滤。
Payload 可以包含文本片段、文件路径、项目名称、版本等信息；原文也可以存放在其他系统中，
由检索结果中的标识或路径定位。

Qdrant 是 RAG 的一个可选组件，不能单独替代完整的 RAG 流程。

** 各组件的职责划分

| 组件                 | 主要职责                                     |
|----------------------+----------------------------------------------|
| AI 客户端，如 Codex   | 接收问题、调度工具、组织上下文与模型调用       |
| MCP 服务端           | 暴露检索接口、校验参数、调用后端并整理结果     |
| Embedding 模型或服务  | 将文本或代码转换为用于检索的向量表示           |
| Qdrant               | 存储向量和 Payload，执行检索与过滤            |
| 大语言模型（LLM）     | 结合用户问题和检索资料生成回答                 |

这是一个常见的职责划分，并非固定的部署要求。例如，Embedding 和重排可以由独立的 RAG
后端完成，MCP 服务端只负责转发请求；服务端也可以自行维护缓存或持久化数据。

* Rust MCP 服务端需要嵌入 Rust 项目吗？

*通常不需要。* 为 Codex 提供能力时，Rust MCP 服务端可以是一个独立程序，
不必作为依赖嵌入待分析或待开发的 Rust 项目。

这里需要区分“用 Rust 编写服务端”和“将服务端嵌入业务进程”：前者是语言选择，后者是
部署方式。根据实际需求，也可以在已有应用中加入 MCP 接口，复用其业务逻辑。

** 常见的通信方式

- =stdio=：客户端通常启动服务端子进程，通过标准输入、标准输出交换协议消息。
  这条连接不需要额外监听网络端口，适合本地工具。
- =Streamable HTTP=：客户端通过 HTTP 端点连接服务端，适合独立部署或供多个客户端访问。

旧版 HTTP+SSE 传输已被 Streamable HTTP 取代，但 Streamable HTTP 本身仍可使用 SSE
传送流式消息。因此，不宜将远程传输笼统写成“HTTP/SSE”，也不能理解为 SSE 已完全弃用。

使用 =stdio= 时，标准输出应保留给协议消息，日志应写入标准错误，避免破坏通信。
即使 MCP 连接使用本地管道，服务端访问远程 Qdrant 或 Embedding API 时仍会产生网络通信。

参考：[[https://modelcontextprotocol.io/specification/2025-06-18/basic/transports][MCP 传输规范（2025-06-18 版）]]。

** Codex 接入示例

假设已经编译好一个使用 =stdio= 的 Rust MCP 服务端，可通过以下命令注册：

#+begin_src sh
codex mcp add my-rust-server -- /absolute/path/to/your-rust-mcp-server
#+end_src

将示例路径替换为实际可执行文件的绝对路径。注册的是服务端启动命令，不是 Rust 源码文件。

也可以在 =~/.codex/config.toml= 中配置同一个服务端；以下方式与上面的命令二选一即可：

#+begin_example
[mcp_servers.my-rust-server]
command = "/absolute/path/to/your-rust-mcp-server"
#+end_example

受信任项目还可以使用项目级的 =.codex/config.toml=。配置后，可运行 =codex mcp list=
查看已配置的服务端，在 Codex TUI 中使用 =/mcp= 查看活动服务端。

上述示例只配置 Codex 到 MCP 服务端的连接。Qdrant 地址、认证信息和 Embedding 模型等，
仍需按所用服务端的配置方式设置。

参考：[[https://developers.openai.com/codex/mcp][OpenAI 官方 Codex MCP 文档]]。

* MCP 如何与 RAG、Qdrant 协作？

典型实现分为两个阶段：先将资料处理并写入检索系统，再在用户提问时检索相关内容。
仅连接 Qdrant，并不会自动让 AI 获得尚未入库的项目知识。

** 资料入库阶段

1. 读取代码、文档或其他知识源。
2. 按适合检索的粒度切分内容，并保留来源信息。
3. 使用 Embedding 模型为片段生成向量。
4. 将向量及相关 Payload 写入 Qdrant 的 Collection（集合）。
5. 当原始资料变化时，同步更新或删除对应记录，避免返回过期内容。

这部分工作可以由独立脚本、后台任务或 MCP 写入工具完成，不必在每次提问时执行。

查询向量与资料向量需要位于兼容的向量空间，通常使用同一套 Embedding 模型及配套设置。
仅仅保证向量维度相同，并不能保证语义检索有效。

** 查询与回答阶段

以“查找项目中用户鉴权的实现”为例，一种常见的流程如下：

#+begin_example
用户提问
   |
   v
AI 客户端（如 Codex）
   | 调用 search_knowledge_base 工具
   v
MCP 服务端 / RAG 后端
   | 将问题转换为查询向量，并设置过滤条件
   v
Qdrant
   | 返回匹配记录、相关分数和所请求的 Payload
   v
MCP 服务端 / RAG 后端
   | 提取文本及来源，按需重排、去重、截断
   v
AI 客户端
   | 将选取的检索资料纳入模型上下文
   v
大模型生成回答
#+end_example

MCP 服务端通常返回可供模型理解的文本、结构化结果或资源链接，而不是单纯把原始向量
交给模型。若原文未保存在 Payload 中，还需要根据记录中的标识回源读取。

是否调用工具、何时调用，以及把哪些结果加入上下文，由客户端的工作流和权限策略决定。
注册服务端不代表每次提问都会自动执行检索。

** 检索工具的接口设计

例如，服务端可以公开名为 =search_knowledge_base= 的工具，接受查询文本、结果数量上限
和项目范围等参数。以下仅为自定义工具的参数示意，并非 Qdrant API 或完整 MCP 消息：

#+begin_src json
{
  "query": "用户鉴权的实现在哪里？",
  "limit": 5,
  "project": "my-rust-project"
}
#+end_src

工具结果宜包含文本片段、文件路径或文档地址，以及必要的版本和定位信息，便于模型说明依据，
也便于用户回到原始资料核查。返回数量与文本长度应受到控制，避免无关内容占满上下文。

在 Rust 实现中，可以通过 Qdrant 的 Rust 客户端 =qdrant-client= 调用数据库。
Embedding、权限过滤和结果组织属于应用逻辑，不会因为接入 MCP 就自动完成。

* Tools、Resources 与 Prompts 的区别

这三者是 MCP 服务端可提供的不同能力，不能都理解成“自动向模型注入上下文”。

| 能力      | 用途                         | 在知识库中的示例                   |
|-----------+------------------------------+------------------------------------|
| Tools     | 执行带参数的操作             | 搜索文档、按授权写入知识片段       |
| Resources | 提供可读取的数据             | 读取指定文档或项目概览             |
| Prompts   | 提供可复用的提示词模板       | 生成带来源说明的知识库问答提示     |

** Tools：适合按问题动态检索

检索工具接受查询条件并返回结果，是将 Qdrant 检索能力提供给 AI 客户端的一种直接方式。
写入、删除等操作也可以公开为工具，但需要由服务端实际实现，并由相应权限策略约束。

** Resources：提供可定位的数据

服务端可以设计 =qdrant://project-docs/overview= 这样的资源 URI，并实现读取逻辑。
这只是自定义资源标识的示例，不是 MCP 或 Qdrant 内置的集合映射规则。

声明资源不会自动把某个 Collection 的内容加入模型上下文。客户端必须支持资源读取，
并在具体交互中选择读取及使用这些内容。

** Prompts：提供提示词模板

服务端可以提供“根据检索结果回答，并列出来源”之类的模板。
模板本身不等于检索执行，也不会自动触发 Qdrant 查询；实际流程仍由客户端和应用逻辑组织。

不同客户端对上述能力的支持程度和交互方式可能不同，接入时应分别确认。
参考：[[https://modelcontextprotocol.io/docs/learn/architecture][MCP 官方架构与能力说明]]。

* 使用 MCP 的优势与边界

** 降低多个客户端之间的重复适配成本

同一套检索逻辑通过 MCP 暴露后，可以被多个兼容客户端复用，减少为每个客户端单独设计接口
的工作。实现语言与客户端语言也可以不同。

这种复用有前提：双方支持相应的协议版本、传输方式和能力。“支持 MCP”不代表所有功能
都能无配置、无差异地使用。

** 将客户端接入与检索实现分开

MCP 服务端可以集中处理参数校验、身份验证、权限过滤和结果格式化。
后端更换向量模型、增加重排或调整数据源时，只要工具接口保持兼容，就能减少客户端改动。

MCP 不会自动改善检索质量。切分方式、模型选择、索引更新和排序策略，仍然需要单独设计。

** 支持本地部署，但不自动保证数据留在本地

MCP 服务端和 Qdrant 都可以部署在本机或私有网络中，让应用控制可查询的范围及返回内容。
但“本地运行 MCP”不能推出“数据不出本地”：

- 使用云端 Embedding API 时，待嵌入的文档或查询文本可能被发送到该服务。
- 使用云端大模型时，被加入模型上下文的检索片段可能被发送到模型服务商。
- 服务端能访问哪些文件、数据库和网络，取决于实际权限与部署设置。

因此，数据流向需要结合整条链路判断，不能仅凭 MCP 的部署位置判断。

** 与直接调用 RAG API 的比较

| 维度           | 直接调用 RAG API                       | 通过 MCP 接入 RAG                       |
|----------------+---------------------------------------+-----------------------------------------|
| 接口适配       | 按应用约定设计与集成                   | 利用标准协议及工具发现机制               |
| 客户端复用     | 取决于 API 约定和客户端集成方式        | 多个兼容客户端可复用服务端               |
| 部署方式       | 可以本地、内网或云端部署               | 同样可以本地、内网或云端部署             |
| 权限控制       | 由应用与基础设施实现                   | 仍需由客户端、服务端及基础设施配合实现   |
| 检索质量       | 取决于数据、模型和检索策略             | 同样取决于这些因素                       |
| 开发维护成本   | 单一应用中可能更直接                   | 需维护协议接入，适合多客户端复用         |

如果只有一个自有应用需要检索，直接调用 Qdrant 或现有 RAG API 可能更简单。
如果希望 Codex 等多个 AI 客户端共享同一套知识库能力，MCP 更有助于统一接入方式。

* 现有实现与后续实践

Qdrant 官方维护了 [[https://github.com/qdrant/mcp-server-qdrant][mcp-server-qdrant]]，可以作为了解现有接入方式和配置的起点。
不必为了让 AI 使用 Qdrant，就从零编写一个 Rust 服务端。

如果已有 RAG 系统，可以在现有检索 API 外增加 MCP 接口；如果需要自定义 Rust 实现，
可以先完成“一个只读检索工具 + 一套已入库资料 + 一个客户端”的完整流程，
再根据需要增加写入、资源读取或提示词模板。
